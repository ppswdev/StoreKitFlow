# Swift 6 重构任务拆分与验收

> 方案已确认。以下保留任务定义和 63 个验收场景；实际完成状态、覆盖范围及外部待验项见 [实施与验收记录](StoreKitFlow-实施与验收记录.md)。

| T12 | P0 发布门槛 | Swift Testing 领域测试、XCTest + StoreKitTest 集成、UI 检查、Sandbox 验收清单 | 随 T02–T11 开发 | 关键案例自动化；真实账号依赖项目标明待验证，不假报通过 |
| T13 | P1 | API 迁移、日志脱敏、JSON schema、README/Docs 重写、SPM 发布准备 | T11、T12 | 示例代码可编译；文档与 API 一致；所有主线构建通过 |
| T14 | 条件范围 | SDK 27 组合/套件订阅、承诺期、分期/部分退款、Advanced Commerce 能力评估与适配 | T02、T03、T06；真实商品/文档 | 先给能力和测试结论；具备条件再实现专用策略，不能用普通订阅兜底 |
| T15 | 条件范围 | iOS 15/16、tvOS、watchOS、visionOS 及更多原生 UI 平台适配 | 主线稳定 | 每个平台编译及可用性测试通过后才更新支持矩阵 |

建议实施批次：

1. **M1 基础与规则**：T01–T04；先固定 Pro 和交付行为，再接 UI。
2. **M2 真实流程**：T05–T08；能正确购买、交付、补单、恢复、处理退款和状态变化。
3. **M3 完整示例**：T09–T11；优惠、账号扩展、SwiftUI 集成。
4. **M4 发布质量**：T12–T13；测试是全程工作，最后进行整体验收。
5. **条件扩展**：T14/T15 根据确认范围决定是否进入发布前置条件。

T10 的交付是生产可接入契约和 Fake 实现；真正部署的后端需另有仓库/环境，不能以 Fake 通过替代真实后端验收。

## 2. 核心业务验收矩阵

### 2.1 商品与详情

| ID | 场景 | 预期 |
|---|---|---|
| C01 | 全部商品有效 | 分类、顺序、类型、价格和详情正确 |
| C02 | 部分 ID 不返回 | partial + missingIDs，其余仍可展示 |
| C03 | 全部不返回 | 区分空目录与请求抛错，不猜测审核原因 |
| C04 | 网络错误后重试 | 保留旧目录并标 stale，商品错误不撤销 Pro |
| C05 | 同时多次加载 | 合并请求，更新期间新刷新不丢失 |
| C06 | 商店地区改变 | 失效旧价格/优惠，刷新后 UI 与结算一致 |
| C07 | 日元、三位小数货币、季度/半年和免费试用 | 不固定两位小数，不错算周期，不丢 Decimal 精度 |
| C08 | 新 SDK 字段/未知类型/旧 OS 不可用 | Optional/capability 正确；不崩溃、不伪造值 |

### 2.2 购买流程

| ID | 场景 | 预期 |
|---|---|---|
| P01 | 四类商品分别成功 | 验证、交付、持久化、finish 和权限顺序正确 |
| P02 | 用户取消 | 正常取消，已有 Pro 不变，无失败告警 |
| P03 | Ask to Buy pending 后批准 | 先不授权；后续交易进入同一交付路径 |
| P04 | pending 后 App 被杀死/长时间无结果 | 重启可核对，不自造失败或交易 ID |
| P05 | 连续点击和多窗口同时购买 | 系统购买界面互斥；不重复扣款请求 |
| P06 | 系统购买受限 | 预检/系统结果明确，UI 可恢复 |
| P07 | 购买请求错误和网络中断 | 可解释结果，不能自动重新发起扣款 |
| P08 | 已有永久商品再次选择购买 | 引导已拥有/恢复，不重复交付永久权益 |
| P09 | StoreKit 验证失败 | 不新增权益，不 finish，不输出敏感证据 |
| P10 | 外部交易/原生 StoreKit View 购买 | 成功结果统一处理，不依赖 updates 二次通知 |
| P11 | 优惠不合格、签名过期或错误 | 明确失败，重新选购需用户确认，不偷偷改原价购买 |
| P12 | 合法和非法 quantity | 消耗品按数量交付，其他非法数量在支付前拒绝 |

### 2.3 交付、补单和幂等

| ID | 场景 | 预期 |
|---|---|---|
| D01 | success、updates、unfinished 同时给同交易 | 合并任务；余额只增加一次 |
| D02 | 收到交易后崩溃 | 未 finish，重启补单 |
| D03 | 本地增加余额前/后崩溃 | 账本事务保持余额与去重标记一致 |
| D04 | 服务端发货后客户端超时 | 同幂等键查询/重试，不重复交付 |
| D05 | delivered 后 finish 前崩溃 | 重启只补 finish |
| D06 | finish 后本地状态未更新 | 对账，不重复交付；不伪造 throwing finish API |
| D07 | 同一原始订阅链发生两次续费 | 两个 transaction ID 均被处理，不按 originalID 去重 |
| D08 | 已处理交易后收到撤销修订 | 按证据版本处理撤销，不被旧去重记录吞掉 |
| D09 | 磁盘满、账本损坏或迁移失败 | 阻止未确认交付的 finish；可解释恢复路径 |
| D10 | 未配置商品或账号归属冲突 | 隔离待处理，不误授予 Pro，不阻断无关交易 |

### 2.4 Pro 与订阅

| ID | 场景 | 预期 |
|---|---|---|
| E01 | 首次启动尚未读取 | unknown，不显示“已过期” |
| E02 | 购买有效 Pro 订阅 | active，来源/期限正确 |
| E03 | 有效免费试用后关闭自动续订 | 到期前 active，续订偏好 false |
| E04 | 付费周期中取消 | 当前权益不丢失 |
| E05 | 到期时 App 前台/后台再返回 | 正确重算，不依赖新交易一定出现 |
| E06 | 宽限期且交易原到期日在过去 | active，显示宽限边界 |
| E07 | 宽限结束进入纯重试期 | 该来源不授权；其他来源不受影响 |
| E08 | 续费从重试恢复 | 验证后恢复 active，清理付款提醒 |
| E09 | 终身 Pro + 退款的订阅 | 仍 active，原因保留终身来源 |
| E10 | 多订阅组和多等级 | 按权益映射和声明等级聚合，不按价格猜测 |
| E11 | 同组个人和家庭共享状态并存 | 检查全部来源；撤销其一不错误清空全部 |
| E12 | 升级、下期降级、跨级切换 | 当前/下期方案区分，isUpgraded 旧来源不重复授权 |
| E13 | 非续订默认/累加/退款/重装 | 规则按版本重算；缺历史显示受限，不错误延长 |
| E14 | 无网络、缓存到期、时钟回拨 | 不无限续期；未知与确定失效区分 |
| E15 | 完整权益为空/扫描取消/未验证候选 | 权威空结果清旧权益；不完整结果不冒充权威空 |

### 2.5 管理、退款与恢复

| ID | 场景 | 预期 |
|---|---|---|
| R01 | 关闭管理界面但未取消 | 无取消成功事件 |
| R02 | 管理界面取消后返回 | 刷新确认续订偏好，当前 Pro 保留 |
| R03 | 退款申请提交成功 | requestSubmitted，Pro 不立即关闭 |
| R04 | 用户取消退款请求 | 原权益不变 |
| R05 | 后续退款批准/家庭撤销 | 有证据才判断退款；只删除对应来源 |
| R06 | 重复/乱序退款通知、部分退款 | 幂等补偿，不能用旧证据恢复已撤销授权 |
| R07 | 恢复成功但无权益/有待交付订单 | 准确报告，不统一宣称 Pro 已恢复 |
| R08 | sync 认证取消/失败、多窗口无活跃 scene | 明确结果；未显示界面不返回成功 |

### 2.6 架构和接入

| ID | 场景 | 预期 |
|---|---|---|
| A01 | 重复 start/stop/reconfigure | 唯一监听；无残留后台任务和旧回调 |
| A02 | 账号切换时购买未完成 | 原交易按原归属核对，新快照不串号 |
| A03 | nil/mismatched appAccountToken | 依 AccountPolicy 核实，不随意绑定当前账号 |
| A04 | 多事件消费者和慢消费者 | 广播、可取消、gap 可检测；发货不依赖 UI 消费 |
| A05 | 刷新过程中收到撤销 | dirty 合并补跑，旧结果不覆盖新证据 |
| A06 | 日志关闭和 release 包 | 无完整 JWS/token/设备校验数据泄漏，开关有效 |
| A07 | JSON 导出、大整数、顺序 | schema 稳定，精度无损，转换不偷偷查网络 |
| A08 | SwiftUI Preview | 全离线 Fake，无 sync/购买副作用 |
| A09 | Swift 6 完整检查 | 无 data-race 编译错误，无新增 unchecked 绕过 |
| A10 | unknown enum/new product | 明确降级和能力告警，不按已知类型误授权 |

以上共 63 个编号场景。一个编号可拆成多个测试；不是以测试数量代替业务覆盖。

## 3. 测试分层及外部依赖

| 层级 | 工具 / 内容 | 能证明什么 | 不能替代什么 |
|---|---|---|---|
| 领域单元测试 | Swift Testing + Fake Gateway / Clock / Ledger | Pro 规则、去重、乱序、错误、事件及迁移的确定性 | Apple 真实交易行为 |
| 本地 StoreKit 集成 | XCTest + SKTestSession + `.storekit` 场景 | 四类购买、续订、失败、pending、退款等系统交互 | 生产配置、真实签名/服务端通知 |
| SwiftUI UI 检查 | UI tests / 可复现人工步骤 | scene、loading、按钮、恢复和错误展示 | 对账正确性 |
| Sandbox / TestFlight | 独立沙盒测试账号及真实商品 | 商品配置、优惠资格、跨设备、真实网络及服务端联调 | 生产所有时序和所有账号情况 |
| 发布前回归 | 最低支持 OS + 最新 OS，主线平台构建 | 兼容性和 availability | 未声明平台的支持 |

对 StoreKitTest 无法直接操纵或当前环境无法复现的场景，用 Fake 覆盖规则，再列入 Sandbox 人工验收，必须在记录中区分“自动通过”和“待真实环境验证”。

真实沙盒验收前需要：自己的 bundle/team、四类产品和至少两个订阅组、介绍性/促销/优惠码配置、可选家庭共享、宽限期设置、测试账号；涉及后端时还需通知地址及签名服务。演示产品 ID 不当作生产商品 ID。

## 4. 每阶段验收记录格式

每个里程碑保存以下信息：提交/版本、Xcode/Swift/SDK、运行系统、测试环境、通过场景 ID、失败场景及日志、暂未验证原因、已知限制、迁移影响。

M4 放行必须满足：

- 四类标准产品与 Pro 关键场景无未解决的 P0/P1 业务缺陷。
- 编译、规则测试、交付恢复、StoreKit 本地集成通过；真实环境未验项目明确列出。
- 应用无须设置 `isPro` 即能从快照正确解锁；UI 关闭不影响必要的交易恢复。
- 无提前 finish、重复发货、无依据的免费试用承诺或退款成功提示。
- 支持矩阵与 Package 和工程配置一致。
- README、旧 Docs、示例不再使用已经删除的接口。
- 不自动提交商店；发布 Git 标签和推送依据用户授权执行。

## 5. 迁移和回滚策略

实施前记录当前 git 状态，不覆盖用户已有修改。按任务进行小步改造；修改公开接口时同批更新示例，避免长期不可构建。

账本 schema 采用版本化迁移，不用清空账本解决兼容问题；清空会导致重复发货或余额丢失。发布前保留升级前数据备份和迁移测试样本，不能直接降级到不认识新 schema 的旧代码。

保留旧版文档的历史说明，2.0 文档明确生效版本。商品 ID、已有订单和账号归属不因重构自动变化。按最终确认，本轮不实现旧 API 适配层，已有调用方升级 2.0 时改用 StoreClient。
