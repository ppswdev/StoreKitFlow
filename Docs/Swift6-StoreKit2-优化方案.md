# StoreKit2Manager Swift 6 优化方案

> 状态：方案已确认；本文保留设计依据，最终实现与差异见 [实施记录](StoreKitFlow-实施与验收记录.md)。日期：2026-11-05（Asia/Shanghai）。
> 依据：仓库实际代码、已执行的模拟器编译检查、Apple / Swift 官方资料、本机 Xcode 27.2 / Swift 6.4.2 / iOS 27.2 SDK 接口。来源和版本限制见 [API 核对](Swift6-StoreKit2-API核对与参考.md)。

## 1. 目标和交付边界

将现有封装升级为适合 SwiftUI 应用使用、可测试、可恢复的 StoreKit 2 模块，同时保留一个真实可运行的演示 App。

最终交付包括：四类标准内购的完整客户端流程、明确的 Pro 权益规则、完整交易处理和补单、订阅状态变化、系统管理和退款入口、类型安全的商品与交易详情、SwiftUI 示例、自动化测试、迁移和接入文档。

“完整”指覆盖约定场景及明确处理未知和不可用情况，不承诺客户端能够观察所有离线或后台事件。Apple 的服务延迟、系统界面结果和平台限制必须体现在状态模型里，不用一个 Bool 掩盖。

### 1.1 建议确认的基线

| 决策 | 建议 | 影响 |
|---|---|---|
| 语言 | Swift 6 语言模式，完整并发检查 | 不仅升级 `swift-tools-version`，所有 target 同步检查 |
| 构建 | 首轮以本机 Xcode 27.2 为已知验证环境；最低可用 Xcode 在 T01 验证后写入兼容矩阵 | 不把“Swift 6”与“所有 Swift 6 编译器均可构建”混为一谈 |
| 运行系统 | 主线 iOS / iPadOS 17+；macOS 14+ 核心库适配 | 使用 Observation；若需 iOS 15/16，增加独立兼容任务，不能无声降低兼容性 |
| 其他平台 | tvOS / watchOS / visionOS 作为明确的后续适配任务 | 原 Package 声明不等于已验证；未通过构建和平台测试不宣称支持 |
| 分发 | 按后续确认仅使用 SPM | 未验证前不保留过时的 Swift / 平台承诺 |
| 版本 | 按 2.0 处理公开 API 变更，提供迁移表 | 不强行维持含糊的旧 `isPurchased()` 语义 |
| 商业模式 | 默认无自有账号的 Apple 购买权益模式；可注入服务端及账号策略 | 无后端也能演示四类商品；账号系统不能凭空推断 |
| Pro | 显式配置哪些商品授予 `pro`，不根据商品名字、价格或类型猜测 | 非 Pro 内购不会误解锁会员 |
| 非续订时长 | 按商品配置；默认从本次购买时间起算，不自动累加 | 可显式选购后顺延，规则必须稳定并可迁移 |

用户已确认并授权本地库、示例、测试和文档实现。生产服务端部署、App Store Connect 创建商品、证书配置、发布商店均不属于当前授权动作。

### 1.2 新版 SDK 的范围必须显式说明

本机 SDK 和官方符号页还包含 iOS 27+ `subscriptionBundle`、`subscriptionSuite`，以及承诺期、分期和更细的撤销字段。不能继续声称 StoreKit 永远只有四种产品类型。

第一验收里程碑覆盖四类标准内购。新版类型列入 T14：先确认官方业务语义、账号能力和可测试商品，再补充专用策略及案例；在此之前，保留原始类型、返回明确的不支持能力，不把它们当普通订阅发放 Pro。Advanced Commerce、外部支付也必须独立配置和验收。若产品确实使用这些能力，应把 T14 提升为发布前置条件。

## 2. 当前实现中必须解决的问题

| 现状 | 风险 | 对应改造 |
|---|---|---|
| 示例引用旧状态和属性，代理参数标签不一致 | 无法编译或默默收不到数据 | 新 API、示例、协议、文档同时迁移 |
| 管理器遗漏更新 `latestTransactions` | 最新交易和家庭共享查询错误 | 原子发布一致的状态快照 |
| 购买成功和启动补单提前 `finish()` | 扣款后未交付，尤其是消耗品 | 统一交易流水线和交付确认 |
| 历史购买被当作有效权限 | 到期或撤销后仍可能解锁 | 独立权益引擎和 Pro 聚合 |
| 非续订到期配置没有被使用 | 时长配置无效 | 按商品的期限计算和退款重算 |
| 购买后才启动轮询，取消续订即停止 | 漏报到期、恢复或重新订阅 | 应用级双监听与生命周期刷新 |
| 取订阅组第一个状态 | 同组商品、家庭共享关联错误 | 遍历已验证状态，按交易和权益聚合 |
| 促销文案与实际购买参数不一致 | 展示价格和结算方案不同 | 统一 OfferSelection |
| 错误被吞掉、返回成功含义含糊 | UI 错报成功，业务无法重试 | 类型化结果、错误和诊断 |
| 重复配置和任务清理不完整 | 多监听、旧账号结果串入新状态 | session generation、显式 stop/reset |
| 无自动化测试、日志开关无效 | 回归难发现、交易详情过度输出 | 可替换依赖、测试矩阵、脱敏日志 |

## 3. 架构与并发设计

### 3.1 职责划分

| 模块 | 隔离方式 | 职责 |
|---|---|---|
| `StoreKitClient` | `@MainActor @Observable` | SwiftUI 观察入口，提供不可变快照和命令，不直接推断 Pro |
| `StoreCoordinator` | `actor` | 生命周期、并发命令、商品缓存、监听、刷新合并、事件序号 |
| `StoreKitGateway` | 协议 + 生产适配器 | 封装 StoreKit 查询、验证结果和监听，便于替换为测试实现 |
| `StorePresentation` | `@MainActor` | 当前活跃 scene 的购买确认、订阅管理、退款和兑换界面 |
| `TransactionProcessor` | 由 coordinator 调度的单一处理入口 | 验证、路由、交付、持久化、完成交易；按交易合并并发 |
| `DeliveryLedger` | 独立持久化 actor | 交易处理进度、消耗品余额及发放去重；无 UI 依赖 |
| `EntitlementResolver` | 纯函数 / Sendable 值 | 按证据和配置计算权益、层级、Pro、到期及撤销 |
| `DeliveryHandler` / `AccountPolicy` / `OfferSigner` | `Sendable` 协议 | 可选的业务交付、账号归属和服务端优惠签名 |
| `StoreClock` / `StoreLogger` | 注入依赖 | 可控时间、结构化日志、可复现实验 |

不使用 `@unchecked Sendable` 绕过并发错误，不让 `[String: Any]` 穿过 actor 边界。Apple 类型仅在 SDK 确认 Sendable 的边界内传递，业务跨边界统一使用 `Sendable` DTO。

### 3.2 任务与重入规则

- 应用根部持有一个 client；付费页出现和消失不决定交易监听寿命。
- `start()` 同配置幂等；不同配置必须显式 `stop/reset/reconfigure`，返回可解释结果。
- 监听在读取历史和权益之前注册；注册和快照刷新之间的更新统一合并，不能依赖严格到达顺序。
- 每个交易键保存一个 in-flight 任务；actor 在 `await` 时仍会重入，单靠 actor 不等于业务去重。
- 商品/权益刷新按 scope 合并；刷新期间再收到事件会标记 dirty 并补跑，不能丢弃。
- 每次启动、账号切换有 generation；旧快照不能覆盖新快照。已经付款的旧账号交易仍按原归属交付或等待核对，不能简单丢弃后 finish。
- 停止操作取消监听、定时器及观察者；未确认交付的交易仍可在下一次启动补单。
- 对购买确认等系统操作不盲目超时重试；Task 取消不意味着 Apple 取消扣款。

## 4. 产品类型与交付规则

| 产品 | 交付内容 | 权益来源 | 退款 / 撤销 |
|---|---|---|---|
| 消耗品 | 金币、次数、额度，按 `purchasedQuantity` 发放 | 持久化账本；默认不授予 Pro | 幂等补偿，已消费部分如何处理由业务策略定义 |
| 非消耗品 | 永久功能或终身 Pro | 已验证的当前权益；显式商品映射 | 移除对应授权来源，保留其他有效来源 |
| 自动续订订阅 | 当前周期服务或 Pro | 当前权益 + 订阅组状态 + 已验证续订信息 | 区分关闭续订、到期、宽限、重试、撤销和退款 |
| 非续订订阅 | 固定期间服务 | 已验证交易 + 每商品时长策略 | 重算有效区间，不依赖 Apple 自动管理自定义到期 |

消耗品账本不把 `Transaction.all` 当余额。已完成历史的可用性与系统版本和配置有关；恢复历史不能把已消费商品再次发放。

非续订产品时长用明确单位：固定秒数或日历日/月/年，禁止把一年固定当 365 天、一个月固定当 30 天。累加策略需要完整交易记录和每次授权区间；重复事件不延长时长，撤销后按原策略重算，重装能否恢复完整累加依赖可获得的历史或服务端账本。

## 5. Pro 必须由权益推导

### 5.1 状态模型

`ProStatus` 不是裸 Bool，而是包含 `access: unknown | inactive | active`、`reason`、`sources`、`validUntil`、`freshness`、`evaluatedAt` 和 `nextEvaluationAt` 的快照。

`isPro` 仅为 `access == .active` 的便利属性。UI 在 `unknown` 时显示检查中/重试，不把它直接当成未购买来展示强制付费墙。初始化的默认 false 不能触发撤销或“会员过期”通知。

| 已验证场景 | 该来源是否提供 Pro | 处理 |
|---|---|---|
| 映射到 Pro 的非消耗品仍有当前权益 | 是 | 永久来源；不受另一笔订阅退款影响 |
| 自动续订 `.subscribed` | 是 | 展示当前周期、续订偏好和有效边界 |
| 免费试用有效 | 是 | 单独标注试用；到期和续费后重新计算 |
| 已关闭自动续订，但当前周期有效 | 是 | `willAutoRenew=false` 不撤销当前权益 |
| `.inGracePeriod` | 是 | 结合宽限期截止时间，不用旧交易到期日直接拒绝 |
| `.inBillingRetryPeriod` 且无其他有效权益 | 否 | 不把扣款重试自动当作宽限期 |
| `.expired` / 已确认撤销且没有替代来源 | 否 | 发布权益变化及原因 |
| 退款申请已提交，尚无撤销证据 | 保持原判定 | 请求成功不等于退款成功 |
| `.pending`、用户取消购买、验证失败 | 不产生新授权 | 已有合法 Pro 不受这次失败影响 |
| 非续订仍在业务有效期 | 是，前提是映射到 Pro | 到期由时钟触发重算 |
| 家庭共享仍有有效授权 | 是，前提是策略允许 | 移除共享后只删除该来源 |
| 某个来源退款但还有终身版/另一有效来源 | 是 | 对所有来源做并集和等级聚合 |
| 仅有过期历史或消耗品交易 | 否 | 历史不等于当前权益 |

### 5.2 判定算法

1. 按 bundle / environment / 账号策略建立当前上下文，加载配置中的商品和订阅组映射。
2. 获取 StoreKit 当前权益；遍历验证结果，隔离 unverified 数据；组状态中的交易和续订信息分别验证。
3. 从每个有效来源生成 `EntitlementGrant`，记录产品、原交易链、所有权、服务等级及有效边界。
4. 对已升级旧交易、明确撤销及到期来源做排除；家庭共享遍历所有候选，不取 `statuses.first`。
5. 对非续订采用专门策略；对不同订阅组和永久来源求并集，同权益多等级取配置声明的等级，不能按价格排名。
6. 由配置中的 `pro` 权益计算 Pro。暂停或部分失败的刷新不随意把其余来源清空。
7. 完整有效的权益枚举确认某来源不存在时，要删除旧来源；不能因为结果为空就永久保留旧 Pro。若存在未验证候选或扫描被取消则标记不完整，不能把它当作权威空结果。
8. 原子发布带 revision 的快照，再发布对应变化事件；只在真实变化时发 `proStatusChanged`。

StoreKit 当前权益包含有效订阅和宽限期来源，但不包含消耗品；非续订的自定义期限仍由业务负责。[Apple 当前权益定义](https://developer.apple.com/documentation/storekit/transaction/currententitlements)

### 5.3 离线、时间和不确定性

- 商品请求失败不清空有效权益；商品目录和权益加载分别建模。
- 优先使用 StoreKit 可验证的本地数据。自己的缓存用于加速展示，不能用 UserDefaults 的 `isPro=true` 作为证明。
- 刷新失败时保留仍在有效边界内的已验证授权，并标记 stale；到期后不能仅靠旧缓存无限延长订阅或宽限期。
- 不确定边界或资料不足时返回 unknown / needsVerification，不伪造过期原因；已知永久来源可以继续提供 Pro。
- 前台按最近到期时间重算并刷新，恢复前台时立即重新评估。设备时钟回拨产生疑点时请求重新核实，不悄悄延长。
- 完全离线无法立即知道远端退款；需要严格云端准入时使用服务端权益校验。该限制应写进产品接入说明。

## 6. 购买、补单与 finish 的业务约束

所有入口：本机购买结果、`Transaction.updates`、`Transaction.unfinished` 都进入同一处理器。不能假设本机成功购买还会通过 updates 再通知一次。[Apple 交易监听说明](https://developer.apple.com/documentation/storekit/transaction/updates)

处理顺序：验证 → 上下文/归属检查 → 按交易键合并 → 持久化已见记录 → 幂等交付 → 持久化交付完成 → 完成 StoreKit 交易 → 对账与发布结果。

- 去重键至少包含应用标识、环境和 transaction ID。`originalID` 用来识别订阅链，不能用于去重每次续费；同一链的多次续费有不同交易。
- 已交付但未完成的交易重放只补 finish，不重复发货。
- 本地消耗品账本的“增加余额”和“记录交易已交付”在同一数据库事务提交。
- 若外部发货成功但本地记录失败，下次只能用同一幂等键查询/重试外部发货；单个本地标记不能保证跨系统 exactly-once。
- 未验证、未知商品、账号归属冲突、持久化失败、业务交付失败不得自动 finish。发布需处理事件并有限退避，避免阻塞无关商品。
- 已确认退款/撤销走补偿和权益重算分支，不当作新购买发货；同交易的后续撤销不能被“之前处理过 transaction ID”过滤掉。修订处理键应包含事件类型和 signedDate / revocation 等证据版本。
- finish 本身是非 throwing 的异步接口；任务被中断时标记本地完成状态未知，启动后对账，不臆造一个 StoreKit `finishFailed` 错误。

Apple 对 finish 的要求是已交付内容或启用服务后再调用。[finish 官方说明](https://developer.apple.com/documentation/storekit/transaction/finish%28%29)

## 7. 取消、退款、恢复和订阅变化

- **取消自动续订**：调用系统订阅管理界面，让用户操作；没有通用公开 API 可静默替用户取消。界面关闭只表示关闭，之后刷新确认，不能立刻发取消成功。
- **退款**：提供指定交易的退款申请入口。结果命名 `requestSubmitted` / `userCancelled`，不是 `refunded`。最终根据交易、订阅状态或服务端证据撤销相应来源。[退款 success 的官方含义](https://developer.apple.com/documentation/storekit/transaction/refundrequeststatus/success)
- **恢复购买**：只在用户主动操作时 `AppStore.sync()`；启动和普通刷新不触发可能要求身份验证的 sync。恢复完成可以没有任何权益，不能宣称一定恢复 Pro。
- **宽限期**：保留权益，展示付款问题和宽限边界；续费成功清理提醒。
- **扣款重试**：如果没有宽限权益，不授予该订阅服务；其他永久或共享授权继续有效。
- **升级/降级/跨级切换**：系统决定生效时机；分别显示当前方案和下期 `autoRenewPreference`，不因为用户选择了降级就立即更换当前权益。
- **价格变更**：展示续费价格、同意状态及生效信息；提醒和跳转，不能替用户同意。
- **优惠**：介绍性、促销、优惠码、win-back 分开；选择、资格、签名、结算和展示使用同一个方案。
- **退款与撤销原因**：旧系统只有较粗证据时使用“授权撤销/原因未知”；不能把家庭共享移除一律称为退款。新系统部分退款字段也不能盲目解释为所有权益立即失效。

监听策略以交易流和订阅状态流为主，结合前台/管理界面返回/恢复/购买后的刷新和到期调度。App 挂起时不承诺实时回调；需要后台持续处理时由 App Store Server Notifications V2 补足。

## 8. 服务端和账号扩展的边界

本项目实现可插拔协议、请求/响应模型、Fake 后端和失败示例；没有用户指定的后端仓库、认证、数据库及部署信息时，不虚构生产服务端已完成。

有自有账号时，需要服务端确定订单归属、账户切换、订阅迁移和家庭共享策略。`appAccountToken` 是关联线索，不是客户端认证凭据，缺失 token 的历史/商店外交易不能自动认定属于当前登录用户。

服务端方案覆盖：JWS 验证、bundle/environment 检查、订单和发货幂等、Server Notifications V2 去重和乱序、状态对账、退款消费信息请求、优惠签名。密钥不写进客户端；Apple 的通知是发给服务端，不是直接唤醒任意客户端的推送。

## 9. 方案确认项

以下为原始方案确认摘要；后续明确决策见 [决策记录](StoreKitFlow-决策记录.md)：
